# Daiyu2 开发工作流

## 1. 目标与事实源

采用「路线图 → 当前阶段 → 执行契约 → 交付证据」，按风险轻量执行。工程位置和保护范围见根目录 [AGENTS.md](../../AGENTS.md)。

文档职责见根目录 [AGENTS.md](../../AGENTS.md)。当前状态只维护在 [current_milestone.md](current_milestone.md)；路线图、任务文档和交接入口只引用它。代码与当前 Git 状态优先于历史描述；设计要求以当前用户确认和有效设计文档为准。发现冲突时先说明实际差异，不把目标架构写成已实现事实。

入口文档只做导航；设计维护玩法/画面要求，技术规范维护状态与接口边界，任务计划维护实施批次与验收。批准、当前实现状态和检查结果不复制到其他入口；历史决定注明当时背景。交付检查以本文为准，任务只补本任务特有风险。

## 2. 任务分级

| 级别 | 判断 | 执行方式 |
|---|---|---|
| L1 轻量 | 只读分析、文案、局部低风险调整 | 目标 → 修改 → 对应轻量检查 → 简报 |
| L2 标准 | 已批准边界内的单模块功能批次、内部重构、表现优化 | 目标与验收 → 实现 → 定向检查 → 更新当前阶段 |
| L3 架构 | 状态归属、跨模块接口、账本、模拟规则/时序、存档兼容或重大技术路线变化 | 只读规划 → 用户批准 → 实现 → 集中审查 → 对应检查 → 交付 |

文件数只用于估计工作量。修改很多素材可能是 L2，修改一个账本方法也可能是 L3。同阶段可包含多个级别的任务；相关小项合成一个功能批次。

L2 默认不建独立任务文档。L3 使用 [任务模板](tasks/_TEMPLATE.md)；需要跨批次协调的接口才增加阶段契约，首次只写薄基线。

完整可玩版等跨模块交付用一个里程碑级总计划统筹，按可验收批次执行，不当作单个小任务。批次在当前阶段分别记录状态、实际结果和检查证据，共用总计划；必要时在条目下拆少量执行清单，不为每批建立重复文档。拆批不降低风险等级，也不增加已批准范围内的逐批审批。

## 3. 生命周期与批准

- L1：直接执行并简报。
- L2：`PLANNING → IN_PROGRESS → VERIFY → DONE`。
- L3：`PLANNING → AWAITING_APPROVAL → APPROVED → IN_PROGRESS → REVIEW → VERIFY → DONE`。
- 临时受阻标记 `BLOCKED` 并注明原因、解除条件；放弃标记 `CANCELLED`。
- 文档已写好使用 `AWAITING_APPROVAL`；仅用户明确批准对应开发范围后才能转 `APPROVED`。
- 批准记录包含用户原意、范围和限制。若用户说“继续”，只有已明确指向该开发任务时才作为批准；有歧义先问。
- 权限以当前阶段记录的最新用户授权为准；工作流修改、版本管理设置、游戏开发与发布授权分别判断，不能互相代替。

## 4. 每个功能批次

### 开始

1. 读取当前阶段、关联设计与技术契约；用 `git status --short --branch` 核对已有工作，必要时核对 remote 与最近提交。没有仓库则先说明，不擅自初始化。
2. 说明目标、范围、验收、预计风险和任务级别；高风险任务先确认批准。
3. 明确修改与保留的系统，确认真实运行数据源和玩家入口。
4. 将当前阶段对应任务设为 `IN_PROGRESS`。会话清单可辅助跟踪，不作为跨会话批准凭据。

### 版本管理与恢复

- Git 管理 `Assets/`（含 `.meta`）、`Packages/`、`ProjectSettings/`、文档及必要工具；缓存、玩家包、个人配置和秘密不得纳入提交。远端及当前接入状态只记在当前阶段。
- 首次迁入代码/资产或修改场景/配置前，须有可恢复的本地基线提交；只有初始化和关联远端不算完成保障。若未获提交授权，先请用户提交或授权；临时改用备份也须确认范围，不复制 Library。
- 在可运行功能批次完成后保留检查点；不要求每个小项提交。提交、推送、合并和发布须在明确授权范围内执行，推送前检查范围与敏感内容，不强推、不覆盖远端历史。
- 保留用户已有改动；需要回退时只处理本任务改动，不用广泛重置代替恢复。

### 实现

- 优先复用经批准迁入的正式链路，按纵向可运行批次集成；允许最小核心准备批次，紧接着贯通真实地图、输入、可见反馈与最小保存恢复，不把全部集成风险留到最后。不建独立样片；迁入前核对清单与依赖，不能凭参考工程路径假定本工程已有实现。
- 核心拥有真实状态；表现只读模拟并维护可丢弃缓存；UI 通过现有运行入口发起操作。
- 不因整理目录而一次迁移全部脚本、资源或程序集。资源与 `.meta` 成对保留，保持 GUID。
- 与批准范围不同的模型、存档或状态边界变更，先停在该边界，补契约并重新确认；其他独立已批准任务可继续。
- 不清理他人工作，不触碰真实玩家存档和教程标记作测试准备。

### 审查与完成

- L1/L2 作者自查；相关批次可合并一次审查。
- 架构、账本、迁移/恢复、跨模块变更或最终集成交付，采用一次风险集中的独立审查。工具不可用时记录限制，由主会话复核；不虚构 reviewer/verifier 或其结果。
- 无未修阻断项且满足对应完成条件后标记 `DONE`；部分实现应写实际范围和剩余问题。
- 只更新当前阶段的状态，任务文档保留验收与证据指针。需要长期沿用的边界写回技术规范；决策变化写决策日志或 ADR。

## 5. 契约与决策

- `BASELINE`：由现有代码核实的起点，或用户已批准的约束，注明来源。
- `PROPOSED`：待批准/待实现方案，不能当作已存在 API。
- `STABLE`：实现与对应检查已完成、后续可以依赖的接口。
- 草案明确引入任务、预计消费者和稳定条件；任务结束将实现项转为 `STABLE` 或删除过期草案。
- 没有多个消费者共享的接口不单独建阶段契约。命名、数据单位、状态所有者、依赖方向比预先预测全部方法更重要。
- ADR 使用 [模板](adr/_TEMPLATE.md)，状态为 `PROPOSED / ACCEPTED / SUPERSEDED`；文档落盘不代表决策获批。

## 6. 按风险验证

| 改动 | 最小检查及防止的风险 |
|---|---|
| 文档/工作流 | 相对链接、状态/批准口径、差异检查，防失效入口与越权开工 |
| Unity C# | Unity 编译完成和 Console 脚本错误，防不可加载类型 |
| UI/镜头/世界表现 | 运行正式场景，检查含 HUD 的完整 Game 视图，防黑屏、遮挡、不可见目标和入口缺失 |
| 账本/流动/模拟时序 | 受影响的守恒、容量、规划或推进检查，防重复计水、越权写入和逻辑回归 |
| 存档/世界替换 | 隔离数据的恢复与失败保留检查，防丢档和半切换；不使用真实玩家档案 |
| 构建/资源 | 对应平台构建和启动，防编辑器可用但玩家包缺资源 |

执行前比较最近成功检查与本批变化。未变且已覆盖的检查不重复；失败修复只重跑受影响项目。耗时检查和实包性能采样不并行竞争 CPU。

### Unity 操作

先查 `mcpforunity://custom-tools`、`mcpforunity://instances`，确认连接实例的真实项目路径与目标 `D:/Starwishes/Project/Unity/Daiyu2` 一致，再查 editor state。错误项目只读，不修改、不进入 Play Mode。编译/刷新/域重载完成后检查 Console。

实际 Game 视图必须包含 Screen Space UI；Scene 视图、对象计数与单纯构建成功各自只证明对应事项。在本工程建立/核实构建入口，不直接运行参考工程的构建或 Prepare 脚本。同项目编辑器已打开时用经核实的编辑器构建入口，避免重复启动占用。重设场景、资产或配置不得超出批准范围。

## 7. 本次可玩版快速交付

本节是 M1 可玩版交付检查的唯一清单：直接集成正式链路，省去独立风格试验与长验证阶段；高风险定向检查不能因此省略。

1. 开发中只做 Unity 编译/Console 及实际改动触发的高风险定向检查。
2. 中间批次不反复全构建；最终 Windows 包须覆盖最终交付的运行代码、场景、资源和构建配置。构建后这些内容再变更，须重建并重跑受影响检查；仅文档更新无需重建。启动、短冒烟与截图证据须对应同一最终包体，记录包体路径和构建时间/版本来源，不沿用旧包证据。
3. 完成一次短玩家链路冒烟：普通启动 → 新局/首次教程交接 → 平移缩放 → 引水及催雨有真实反馈 → 暂停返回；在同次运行中用隔离的新模型档案检查保存/恢复，不使用旧真实 v4 档。镜头方向固定，首界面不自动环绕。
4. 亲看一张含 HUD 的完整运行画面，确认基本操作目标可见；不进行多轮主观美术审批。
5. 全量测试、多种子长时运行、多分辨率、性能矩阵、Android 和发行检测后置，逐项标记未执行。短冒烟与截图可在同一次运行中完成。

粗模型额外检查守恒、来源/容量限制、下坡/连通和规划不造水；用隔离新档检查恢复后继续推进及失败保留。核心准备后立即验证最小引水与恢复闭环，后续新增子系统随批次补齐；最终冒烟复用已有有效结果，不重复无关全量。

完成条件：包体可启动；主要操作可用；已知阻断问题已修复；提供启动路径与操作说明。目标 30FPS 只是开发预算，未实测不宣称达标；若实际运行仍因卡顿不能基本操作，应记录 `PARTIAL` 而不是称为可玩版。

用户主观美术认可属于后续试玩反馈，不是 Agent 的重复批准门槛。用户批准开发不等于批准发布。

## 8. 简短交付格式

交付内容及路径；实际检查结果；跳过的检查及原因；已知风险与下一步。独立审查和哈希仅在实际使用时记录用途，未使用时简述即可。源码与文档常规修改不做哈希。
