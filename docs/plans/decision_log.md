## D-001：斜向透视的 2D 风格

- 来源：2026-10-21 当前对话，用户提出美术改为 2D，并明确继续采用「斜向的透视俯视」。
- 约束：保留真正透视的方向，不按先前推荐改成正俯视/纯等距正交。
- 后续选项已确认：2.5D 承载、清爽卡通、固定方向透视；复用核心与玩家流程，见 [设计方案](../design/oblique-2d-playable.md)。

## D-002：工作流先行，确认后才进入开发

- 来源：用户最新要求「先搭建整套工作流，待我确认再正式进入开发」。
- 当时边界：只允许文档搭建，不因计划落盘自动进入开发。后续执行权限只查当前阶段，不以本条历史记录代替授权。
- 工作流参考 WarBrain 的事实源分工、分级和批准机制，沿用 Daiyu 轻量政策；不复制其他项目特定 Agent、游戏架构或权限假设。

- 落地方式：采用 [快速交付最低检查](workflow.md#fast-delivery)，本条不重复维护检查清单。

## D-004：工作目录改为 Daiyu2，旧项目保持原状

- 来源：用户明确指定在 `D:/Starwishes/Project/Unity/Daiyu2` 工作，并要求迁移工作流文档、回退刚才在旧项目的修改。
- 结果：工作流文档位于 Daiyu2；旧项目只撤销本次 Agent 新增/修改的文档，保留原游戏内容。

## D-005：选项决策与开工批准分开

- 来源：用户通过选项选择了 2.5D、核心与玩家流程复用、固定方向、清爽卡通、允许简化水模型、完整基础流程。
- 结果：以这些选择更新设计与执行计划；旧代码作为只读来源，不复制旧三维表现、缓存与整套项目配置。
- 当时权限：用户同时选择「先更新计划再等确认」，设计选择不构成开工授权；后续权限见当前阶段。

## D-006：粗粒度水模型与独立新存档

- 来源：用户选择允许简化水模型，同时保留有限水量、容量、引水和生态规则；新旧存档隔离，不承诺旧 v4 直接兼容。
- 结果：M1 将模型简化纳入范围，不以兼容旧精细几何为第一版前提。保留账本权威、来源/接收限制、真实反馈和完整恢复，新档显式标识模型版本。
- 细化与权衡见 [ADR-002](adr/ADR-002_coarse_water_and_new_saves.md)。模型默认算法属于待开工计划，不把本次文档更新写成已实现。

## D-007：版本管理与审查后的流程收敛

- 来源：2026-10-21 用户要求落实工作流审查修改，并指定 GitHub 仓库作为版本管理工具。
- 决定：采用 Git 管理工程，迁入前保留可恢复基线；首批采用正式链路最小纵向闭环；最终包体覆盖最终交付变更；当前状态与检查证据不在多个入口重复维护。
- 执行规则见工作流，远端地址、接入结果及后续授权只在当前阶段维护；本决定不自动授权游戏开发、提交、推送或发布。
