# M1-01：Daiyu2 斜向 2D 风格正式可玩版

级别：L3。原因：粗水模型、新保存契约，以及镜头/表现/玩家流程跨模块接入。唯一状态/批准记录见 [current_milestone.md](../current_milestone.md)。

本页是里程碑级总计划，不是一次完成的小任务。A～F 是可独立记录结果的执行批次，共用本计划与批准边界；批次内再按实际依赖安排小工作，不另建六份任务文档。

## 目标与依据

在 Daiyu2 落地 [设计提案](../../design/oblique-2d-playable.md)，交付 Windows 可运行目录；直接开发正式链路，不另做独立样片。受 [技术规范](../technical_spec.md)、[ADR-001](../adr/ADR-001_oblique_2d_presentation.md) 和 [快速交付工作流](../workflow.md#fast-delivery) 约束。

工程基线见技术规范。以下旧入口仅为来源参考，不是本工程已有文件；开工须满足当前阶段授权和工作流的可恢复基线要求。

## 执行边界

开发批准后允许：按获批清单选择性迁入必要运行/玩家流程依赖，编写新表现脚本和相关 Shader/材质/贴图、创建正式场景及本工程 Windows 构建入口，进行针对实际热点的行为保持优化。新增小型纯表现组件沿用获批命名空间和单向依赖。保留当前模板与设置，不整体覆盖旧项目 Packages/ProjectSettings。

保护：有限账本、容量/来源限制、实际引水与生态反馈、核心无 Unity 依赖、源工程完整性、旧玩家档案/教程标记、资产 GUID。允许在新工程适配模拟推进、规划/容量模型及新快照，不要求旧 v4 档兼容；不迁移或修改旧真实玩家数据。依赖安装及 Git/发布操作按当前阶段中的独立授权执行。

粗模型的权威状态和新保存边界见 [技术规范](../technical_spec.md) 与 [ADR-002](../adr/ADR-002_coarse_water_and_new_saves.md)。不同时建设通用框架或拆分全部程序集；不新增无限造水、直接改地形、文明或新结局等玩法。

## 预计影响入口

下列路径相对旧参考工程的 `UnityProject/Assets/Daiyu/`；候选目标前缀是 Daiyu2 的 `Assets/Daiyu/`。实施前核对消费者与依赖闭包，明确迁入/重写清单，不照抄旧三维表现和诊断代码。

| 入口 | 本任务职责 |
|---|---|
| `Core/WaterLedger.cs`、`Rivers/Generation/` | 复用账本与生成规则；核实依赖，避免通过生成阶段带入运行时精细水流链路 |
| `Rivers/Ecology/`、`Weather/`、`Groundwater/`、`Cycle/` | 复用规则与算法，适配到单一粗模型；有耦合的部分按模块提取，不并跑两个权威世界 |
| `Gameplay/RiverCameraRig.cs` | 复用透视/平移缩放数学，改为固定方向；移除新工程玩家/菜单环绕入口 |
| `Gameplay/RiverSceneView.cs`、`FixedWaterFootprints.cs`、`LandscapeLook.cs` | 参考贴地、拾取与水况表达；新表现改为清爽卡通，不迁精细水面更新链 |
| `Gameplay/TemporaryLandscapeProps.cs`、`LandscapePropLayout.cs` | 参考布局与生态绑定，重做二维景物/简化岩石与生命周期 |
| `Gameplay/RiverGame.cs`、`MenuFlow.cs` 及 partial | 复用流程语义并适配新世界/保存，单一宿主；不整体照搬旧模拟装配 |
| `Gameplay/PlayerHud.cs`、`Gameplay/PlayerUi/`、必要字体/音频 | 复用 UI 交互与资源，以可读且协调卡通世界为准 |
| `Gameplay/PlayerSaveGame.cs` | 参考完整恢复/原子写文件方法；不迁旧 v4 数据布局作为新模型约束 |
| `Rivers/ChannelGeometry.cs`、`SurfaceRepartition.cs`、旧场景 | 只读参考；新粗模型运行时不依赖精细切割、三角库存重分区或整图几何 successor |

这是复用类别与入口清单，不要求整目录迁入；实现前按实际消费者确认依赖闭包，只迁必要文件和许可资源。正式场景为 `Assets/Daiyu/Scenes/Daiyu.unity`。新增粗模型 API 限于技术规范里的权威世界/命令/快照边界，不预先建设通用架构；必要渲染/输入/构建配置先列明最小变更，不覆盖整套旧配置。

## 分批实施与验收

### A. 复用依赖与粗模型核心（M1-01-A）

首批依赖取舍（2026-10-21 核对源文件）：

- 原样迁入 `Core/WaterLedger.cs`、`Daiyu.Core.asmdef` 及各自 `.meta`，无第三方代码/Unity 引用；不迁 `WaterWorld.cs`，无当前消费者。
- `ProceduralMapGenerator` 的确定性散列与 `NaturalLandscapeMapGenerator` 的平滑噪声/岛岸规则作为提取参考；二者直接引用 `HexRiverMap`、生态、天气、地下水、海洋及 `RiverWorld`，不整文件迁入。新建 `Daiyu.Simulation`，实现版本化静态六边形顶点图、有限节点库存及固定 Tick 转移；不依赖旧 Rivers。
- A 仅迁用户指定旧工程内的核心源码，不迁字体、音频或外部素材；源根未发现 LICENSE 文件，不据此声称第三方素材获得许可。后续素材须单独核实。
- `Gameplay`、旧场景与构建代码不进入 A。B 在同一粗世界上接入新宿主，不建立旧世界适配双轨。

A 的实际接口、检查证据和状态见当前阶段，不在此重复维护。

- 核实候选消费者、依赖闭包与资源许可，在本计划收敛必要迁入/重写清单；不搬精细几何、旧表现整套依赖或诊断装配。
- 选择性迁入账本、必要生成规则，建立无 Unity 依赖的粗世界、真实种子地图和固定业务 Tick；明确状态所有者、单位与命令/快照边界，不建设通用框架。
- 以静态邻接、粗容量/水头近似决定转移，规划只改连接，库存转移只走账本，不重切地形或重分三角库存。
- 退出条件：核心可编译并通过最小定向检查，覆盖真实地图上的连通/方向、来源不足、接收满、转移守恒及规划不造水；记录依赖取舍和 B 可依赖的实际接口。此时只完成核心，不称可玩。

### B. 正式场景引水与最小恢复闭环（M1-01-B）

- 依赖 A；建立唯一运行宿主及正式场景，接基础地形/水路显示、固定方向相机、平移缩放、拾取和引水输入。
- 通过正式命令边界完成“选含水起点 → 规划 → 提交 → 真实来水 → 可见反馈”，不等美术完善再验证交互。
- 建立独立新档，完整覆盖本批已存在的权威状态、时钟与速率余量；验证保存、恢复后继续推进及失败保留。后续新增状态同步扩展，不另建临时保存系统。
- 退出条件：上述闭环在正式场景可操作，显示/拾取一致、规划不造水，恢复后仍可推进且守恒，失败不丢当前局/原档。可在编辑器检查，不增加独立样片、玩家包或美术批准门槛。

### C. 天气、生态、地下水与视野（M1-01-C）

- 依赖 B；将土壤、生态、天气、地下供泉和水况视野接入同一粗世界，催雨扣当地大气，不启用后台第二权威世界。
- 固定业务 Tick 与分频速率有明确时间单位；新增权威状态/余量同步进入 B 的快照，使用基础显示提供可见反馈。
- 退出条件：引水/催雨对真实水况和生态有可见影响，相关收支经过同一账本；受影响定向检查通过，新增系统恢复后可继续推进。

### D. 卡通世界与交互可读性（M1-01-D）

- 依赖 B 的显示/拾取及 C 的真实状态；完善连续大色块地势、二维植被、简化岩石及轻量云雨/雾，不替换已有权威运行链。
- 水带/积水区分规划、空路、来水、干涸，流纹表达真实方向；固定相机无玩家旋转，环境效果只读真实天气/视野。
- 使用分块合批、脏更新，保留实时预览；景物不抢拾取、不遮挡关键水端/河路，切换时资源可释放。
- 退出条件：干湿、水路和生态变化清楚，画面与拾取一致，基础操作不因遮挡或明显卡顿受阻；不增加多轮主观美术批准。

### E. 完整玩家流程与存读档（M1-01-E）

- 基于 B/C 的命令、宿主和保存链路接入首界面、随机新局、简短教程、HUD、暂停返回；教程条件使用新模型实际行为，首界面不自动环绕。
- 补齐玩家进度与完整流程状态，按技术规范核对快照完整性；缓存重建，不把贴图网格入档。数据隔离与候选世界切换遵循技术规范。
- 退出条件：正常入口可完成新局/教程交接、引水、催雨、反馈、暂停返回及完整保存恢复；恢复失败保留当前局/原档，旧玩家档案/标记不变。流程接线可在 B/C 接口可用后提前进行，最终退出须与 D 的正式表现集成。

### F. Windows 集成与交付（M1-01-F）

- 依赖 A～E 完成；修复黑屏、入口缺失、显示/拾取不符、长时间卡顿等阻断问题，不为画风调整反复增加整套验证。
- 建立本工程 Windows 构建入口，不执行旧脚本或 Prepare，交付完整目录与启动/操作说明。
- 退出条件：通过工作流快速交付清单；最终包覆盖最终交付运行内容，启动/冒烟/含 HUD 画面证据对应同一包体，跳过项与剩余风险明确。

### 执行与进度约定

- 推荐顺序 A→B→C→D→E→F；允许按上述真实依赖提前接线或调整，不把 C/D/E 全做完才第一次集成。
- 每批开始和结束在当前阶段更新对应条目，记录实际可运行/可验证结果、检查与剩余问题；部分完成不标 `DONE`，总任务只有 F 交付满足后才能完成。
- 单批若仍过大，在同一条目下列少量执行清单，不增加任务文档、逐项审批、独立样片或每批全构建；接口和高风险改动按工作流集中审查。
